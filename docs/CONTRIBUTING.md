# Contributing to Gooey Wheel

Gooey Wheel is a radial actions menu for macOS that opens from a mouse button. [USERS.md](USERS.md) describes how users interact with it: what every input, menu item, and panel does.

## Building

You need macOS 14 or later and Xcode for the Swift toolchain. There are no other dependencies to install. Sparkle is downloaded by SwiftPM on the first build.

```sh
./scripts/build-app.sh
open "build/Gooey Wheel.app"
```

`build-app.sh` builds a release binary, wraps it in `build/Gooey Wheel.app` with the icon, the welcome video, and Sparkle, and signs it. The app appears in the menu bar, not the Dock.

The script signs with your Apple Development certificate if you have one. That matters more than usual here, because macOS ties the Input Monitoring and Accessibility grants to the signature. Without a certificate the app is signed ad hoc, the signature changes on every build, and you'll have to grant the permissions again after each one. Any free Apple Development certificate from Xcode works.

For a quicker loop that skips the app bundle, build and run the binary directly:

```sh
swift build -c release --disable-keychain
"$(swift build -c release --disable-keychain --show-bin-path)/GooeyWheel"
```

`--disable-keychain` stops SwiftPM from looking for GitHub credentials in your keychain, which can leave it waiting on a permission prompt. A binary run this way uses your terminal's privacy permissions, not the app's.

## Finding your way around

All app code is in `Sources/GooeyWheel`, with the actions in `Sources/GooeyWheel/Actions`. [ARCHITECTURE.md](ARCHITECTURE.md) explains how the pieces fit: the Metal renderer, the spring-driven simulation, the action catalog, and the two ways the app reads the mouse.

| Path | Contents |
| --- | --- |
| `Sources/GooeyWheel` | The app |
| `Sources/NowPlayingHelper` | A small Objective-C library that reads the playing track |
| `scripts/` | Building, releasing, and rendering the welcome video |
| `assets/` | The app icon and the welcome video, both generated by the app |
| `docs/` | These documents |

## Adding an action

Most contributions are new actions, and they follow the same steps.

1. Add an `ActionDefinition` to its category in `ActionCatalog+BuiltIn.swift`. Pick an id in the form `category.name`. The id is saved in people's wheels, so it can't change after release.
2. Add its behavior to the `behaviors` dictionary in the matching file in `Actions/`, under the same id. A plain action needs a `run` closure. A control needs the hooks for its kind; a toggle, for example, needs `isOn` and `run`.
3. If the action only works on some Macs, give the behavior an `isAvailable` check, so the bubble is drawn faded instead of failing.
4. Add a check to that file's `tests` list if the action can be checked without visibly changing anything.
5. Add a row to [ACTIONS.md](ACTIONS.md).

If you're replacing or merging an existing action, map the old id to the new one in `ActionCatalog+Migration.swift` rather than deleting it. Otherwise items in people's saved wheels lose their action.

## Checking your change

Run the self-test before opening a pull request:

```sh
"$(swift build -c release --disable-keychain --show-bin-path)/GooeyWheel" --self-test
```

It's safe to run while you use your Mac: it doesn't move your pointer, send keys to your apps, or change your settings. The `catalog` checks catch the common mistakes in a new action, such as a missing behavior or an SF Symbol that doesn't exist.

For changes to how the wheel looks or moves, the demo modes play scripted interactions and can write each frame to disk. [TESTING.md](TESTING.md) covers them, along with the mouse input log for button problems.

CI runs on every pull request. The CI workflow builds the release binary on a macOS 26 runner, runs the full self-test, builds and verifies `Gooey Wheel.app`, and captures the tour script and the welcome panel off screen. The app and the captured images are attached to the run for 14 days. It skips pull requests that only change docs. The Lint workflow checks the workflows with actionlint, the scripts' zsh syntax, and the links between docs. The PR title workflow checks the title against the format in [Pull requests](#pull-requests).

Some things can only be checked by hand: pressing a Logitech mouse's buttons, haptic taps, and the Bolt receiver. Say in your pull request which of these you tried and on what hardware.

## Pull requests

Branch from `main` and keep each pull request to one change. Titles follow [Conventional Commits](https://www.conventionalcommits.org): a type, an optional scope, and a short lowercase description of the change, such as `feat: read the thumb button through a Logi Bolt receiver` or `fix(panels): stop panels overshooting on close`. The types are `feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, and `chore`, and the title has no trailing period.

In the description, say what changed and why. If the change is visible, include a screenshot or a short screen recording. A recording is better for anything that moves.

Update the docs in the same pull request when behavior changes. Instructions for users go in the README, how the app responds to users in [USERS.md](USERS.md), actions in [ACTIONS.md](ACTIONS.md), and internals in [ARCHITECTURE.md](ARCHITECTURE.md).

## Style

Match the code around you. Comments explain why something is done, or what a reader couldn't work out from the code; they don't repeat the code. Doc comments describe what a type or property is for, as in `ActionCatalog.swift`.

UI text and docs are plain and specific. Say what something does in as few words as it takes, and leave out helper text unless it prevents a mistake.
